# 中达瑞和多光谱拼图：可实现方案

> 依据：`需求材料/多光谱拼图需求 0908评估.xlsx`、`0611hsl_Report.pdf`（LiMapper 4.0）、实测架次 `MAX_20251017`、现有算法 `#15/#16/#17/#19`。  
> 额外约束：约 **10 km × 100 m** 条带，墙钟 **约 30 分钟** 完成拼接，成果可上地图。  
> 代码落点：`algorithm/projects/数据融合/prod/source/`（独立拼图引擎，不把现有融合 HTTP 服务硬撑成 LiMapper）。

---

## 1. 结论先说

**30 分钟能交付可上地图的 RGB + 7 波段正射 GeoTIFF + 质量报告；不能在 30 分钟内复刻厂商「空三 + 全量密集点云 + DSM 逐像素拼图」的完整摄影测量闭环。**

原因不是工程偷懒，而是厂商自己的样例已经给出时间下界：

| 项目 | LiMapper 样例 `0611hsl` | 本次 30 分钟目标 |
| --- | --- | --- |
| 影像 | 1896 张（约 237 曝光 × RGB+7 波段） | 约 400–800 曝光 × 8 组，约 3200–6400 文件 |
| 面积 | 0.101 km² 面状测区 | 10 km × 0.1 km = **1.0 km² 条带** |
| 对齐 | **25.9 min** | 必须压到 **≤ 8 min** |
| 密集点云 | 10.3 min（高、2.5D） | 30 分钟档 **跳过** |
| DSM | 10 s（0.094 m） | 用 POS 平面 / 公开 DEM，或复用已有 DSM |
| 正射 | 11.7 min（0.047 m，DSM 逐像素） | **≤ 12 min**，共享主波段几何 |
| 合计 | **约 48 min / 0.1 km²** | **约 30 min / 1.0 km²** |

若按面积或按影像数线性外推 LiMapper，10 km 条带会落到 **1.5–4 小时**。要进 30 分钟，必须做三件厂商需求里已经允许、但样例软件没有走的捷径：

1. **只对主波段做匹配与几何**（REQ-04-01：默认绿波段，其余刚性配准）。
2. **用文件内 POS 限制像对搜索**，做条带顺序匹配，而不是 8 组独立空三。
3. **30 分钟档不重建密集点云**；DSM 用 POS+AGL 平面或 Copernicus DEM；正射用直接地理定位 + 重叠区特征 refinement。

测绘级 DSM 拼图作为第二档 `survey`，不计入 30 分钟验收。

## 1.1 输入就是拍完后的那一个目录

作业交付物不是单独的 POS 包、也不是已经切好的航带 GeoTIFF。飞完之后对方给出的就是类似：

```text
MAX_20251017_001/
  MAX_0001_Color_D.jpg
  MAX_0002_450nm_W.tif
  MAX_0003_550nm_D.tif
  MAX_0003_Color_D.jpg
  ... 几千个文件平铺在同一层 ...
```

入口只有这一件事：

```bash
python -m ms_mosaic run \
  --input .../MAX_20251017_001 \
  --out  .../runs/MAX_20251017_001
```

程序自己做：按文件名认出 RGB / 波段 / `_D` 作业帧 / `_W` 白板；从每张 JPG/TIF **内部**读 GPS 和姿态；用 `CaptureUUID` 或同一编号把一次曝光的 1 张 RGB + 7 张光谱捆成一帧；然后拼图、写质量报告。

不要求：`pos.csv`、时间戳 JSON、相机 XML、DEM（`fast` 档用 POS+AGL 平面）、人工分组、先转 GeoTIFF。这些有则用，没有也能跑。10 km 条带同样是「又一个这种目录，文件更多」。

xlsx 共 7 组。按「30 分钟条带能否做」分成三档。

### 2.2 做成「有则更好」，不能挡 30 分钟

| 编号 | 名称 | 处理 |
| --- | --- | --- |
| REQ-02-01/02/03/04 | 密集点云 + DSM | `survey` 档再做 2.5D；`fast` 档用平面/公开 DEM |
| REQ-03-02 | DSM 逐像素 / 智能绕行 | `survey`；`fast` 用 POS 正射 + 距离羽化 |
| REQ-03-05 | 智能拼接线 | `survey` 用图割；`fast` 用距离羽化（现有 `#17` 已有） |
| REQ-07-02 | 断点续跑 | P1：按航带写 checkpoint |
| REQ-07-03 | CUDA | P1：`cv2.remap` / 相位相关走 GPU，无卡自动 CPU |

### 2.3 不能按字面承诺，必须和对方改口径

**REQ-05-01：每个波段抽 20–30 点，与野外 GPS 真值比，平均误差 < 2 像素。**

xlsx 自己写了 TBD。实测数据：

- `Camera:RtkUsage = 0`
- `GPSXYAccuracy = 3 m`，`GPSZAccuracy = 5 m`
- LiMapper 样例 **GPS 配准 RMSE = 6.28 m**（平面约 0.7–0.9 m，高程 6.2 m），**0 个 GCP**

本架次 GSD≈0.05 m 时，2 像素 = **10 cm**。没有 RTK / GCP，绝对定位不可能优于 GPS 的 3 m 级。  
可验收的改写：

1. **波段间相对误差 < 2 像素**（绿波段为基准，其余 6 个光谱 + RGB 抽点）。
2. **相对 GPS 的平面 RMSE 作为报告项**，不设 10 cm 门槛；有 GCP 后再启用绝对 < 2 像素。

这不是降低需求，是避免用做不到的绝对精度去验收一套无 RTK 航飞。

## 3. 真实数据已经证明什么

架次 `MAX_20251017_001`，相机 **Wayho MAX-S810**，软件 V0.6.21 / XMP `softVersion V3.2.3`。

| 项 | 实测 |
| --- | --- |
| 文件 | 5362：JPG 671 + TIF 4690 + 1 个重复 zip |
| 曝光 | 671 帧；`0001` 仅 RGB；`0002`/`0671` 为 `_W` 白板；其余 `_D` 为作业帧 |
| 尺寸 | 全部 2048×1536；RGB uint8 JPG；光谱 uint16 未压缩 TIFF（约 6.3 MB/张） |
| 波段 | Color + 450/550/650/720/750/800/850 nm，FWHM=20 nm |
| POS | **RGB 与 TIF 都有**。TIF **不是 GeoTIFF**（无 CRS、无仿射），POS 在 GPS IFD + XMP |
| 姿态 | 相机 `Pitch ≈ -90°`（接近真下）；`Yaw` 随航向；`UAVPitch` 是机体俯仰，正射要用 **Camera Yaw/Pitch/Roll** |
| 航高 | 作业帧 AGL ≈ 110–113 m；起飞帧 AGL=0 |
| 定位 | 无 RTK；GPS 全覆盖 671/671 |
| 轨迹 | 折线约 **8.7 km**，外包约 556 m × 512 m（0.28 km²），时长 11:44–12:13 |
| 厂商成品 | `拼图结果/`：`Orthomosaic_pix_surf_group0.tif`（RGBA，0.05 m）+ group1–7（uint16）+ `DSM.tif`（0.11 m），**EPSG:32647** |

同曝光用 `CaptureUUID` 绑定。例如 `MAX_0003` 的 Color 与 450/550 nm 都是 `20251017f20f590e`，经纬高一致，`RigCameraIndex` 不同（Color=1，Green=0，Blue=3）。  
**几何只求一次，8 路共用。**

厂商成品证明：对方心里的「大图」是 **UTM GeoTIFF 正射**，不是简单拼贴。质量报告由 **LiMapper 4.0** 生成，不是 Pix4D；XMP 命名空间用了 Pix4D Camera，只是为了让摄影测量软件能读 POS。

## 4. 现有仓库差在哪里

`algorithm/source/algorithms/` 的 `#15–#19` 是「已有地理参考的条带 → 套合」，服务的是另一份 12 km² / 0.3 m 的融合文档，**不能直接吃这套 MAX 原始帧。**

| 能力 | 现状 | 本任务需要 |
| --- | --- | --- |
| 读 MAX XMP/GPS | 无 | 每帧 POS + 波段名 + CaptureUUID |
| `#15` 粗定位 | 中心点 + 北向上仿射，**不用姿态** | 必须用 yaw，条带会转 80° |
| `#16` 正射 | **整包一个** alt/roll/pitch/yaw；输出与输入同尺寸；scipy 逐像素 | 每帧外方位；写到统一 UTM 格网 |
| `#17` 镶嵌 | 已有 CRS 的条带羽化 | 可用，但输入必须先是正射 GeoTIFF |
| `#19` 配准 | 整景一个平移 | 帧级 / 分块，且应发生在主波段网格上 |
| 空三 / 点云 / DSM | 无 | `survey` 档另做，不走现有 API |
| 质量报告 | 算法 JSON | 对齐 LiMapper PDF 章节 |

因此：`prod/source` 新建 **条带拼图引擎**，只复用 `common.rs.mosaic` 的分块羽化写出、以及 `#19` 的相位相关思想。不要把 670 张原图 POST 进现有 HTTP 服务。

## 5. 三条技术路线

### 方案 A — 复刻 LiMapper（COLMAP / OpenMVG + OpenMVS）

8 组独立或主波段空三 → 密集点云 → DSM → 逐像素正射。  
**质量最接近 `拼图结果/`，时间对 10 km 不可接受**（样例 0.1 km² 已 48 分钟）。作为 `survey` 远期，不作为 30 分钟交付。

### 方案 B — 纯 POS 直投 + `#17` 羽化

每帧用 XMP 直接地理定位，不做特征匹配。  
实现最快，**接缝会随 3 m GPS 和 1° 姿态噪声错开数米到十几米**，上地图能看，农业指数能凑合，过不了波段 2 像素相对验收。

### 方案 C — 主波段条带匹配 + POS 先验正射（推荐）

POS 限制候选像对 → 只在 **550 nm**（或 RGB）做顺序匹配 → 相似变换/仿射修正外方位 → 统一 UTM 格网正射 → 其余波段 **拷贝同一 warp** → 分块羽化写成 COG → 质量报告。  
这是唯一同时满足「可上地图、波段套合、30 分钟」的路径。

**默认采用方案 C，产品分成两档：**

- `fast`（30 分钟验收）：C，无密集点云。
- `survey`（质量对齐厂商成品）：C 的几何 + 2.5D DSM + 拼接线，不承诺 30 分钟。

## 6. 推荐架构

```text
MAX 目录
  → ingest（建帧目录、解析 XMP/GPS、按 CaptureUUID 成组、滤白板/大倾角）
  → master geometry（550 nm：POS 初值 + 条带顺序匹配 + 可选航带 BA）
  → grid（按航高算 GSD，UTM 带号，10 km 条带外接矩形）
  → ortho master（cv2.remap 到格网，分块）
  → transfer bands（同一套 RPC/单应，7 光谱 + RGB）
  → mosaic（距离羽化；survey 改图割拼接线）
  → report（JSON 明细 + PDF 摘要）
  → out/{dsm,mosaics,process,log,report}/
```

### 6.1 模块与文件（均在 `prod/source/`）

| 模块 | 职责 |
| --- | --- |
| `catalog.py` | 扫描文件名；读 JPG EXIF/XMP、TIF tag 700/GPS IFD；输出 `frames.parquet` 或 JSONL |
| `pos.py` | 经纬高、Camera/UAV 欧拉角、AGL；WGS84 → UTM |
| `filter.py` | `_W`、AGL<5 m、\|pitch+90\|>60°、过曝/过暗 |
| `match_strip.py` | 只匹配时间相邻 + POS 距离 < 1.5× 航向间距的主波段对；ORB/AKAZE + 网格均匀 + RANSAC |
| `pose_refine.py` | 每帧 4 自由度（dx, dy, dψ, ds）或仿射；POS 作先验 |
| `ortho.py` | 针孔 + 可选 k1–k3；DEM 双线性；`cv2.remap`；禁止 scipy 整幅 `map_coordinates` |
| `band_transfer.py` | 同 UUID 共用 remap 表；再对绿波段做 1 次分块相位相关，把残差限制在 2 像素内 |
| `mosaic_write.py` | 调用/改写 `common.rs.mosaic.mosaic_paths_to_path`，COG + LZW，光谱不匀色 |
| `report.py` | 对齐 `0611hsl_Report.pdf` 字段，出 `quality.json` + `quality.pdf` |
| `cli.py` | `python -m ms_mosaic run --input ... --mode fast --out ...` |

### 6.2 几何约定（必须写死，避免 #16 的坑）

1. 输出 CRS：按数据中心经度选 UTM，本测试架次为 **EPSG:32647**（与厂商成品一致）。
2. 正射用 **Camera:Yaw/Pitch/Roll**，不要用 UAVPitch（机体可达 -20°，相机仍接近 -90°）。
3. XMP 主点 `(720, 540)` 对应 LiMapper 报告里的 **1440×1080** 相机组。实图 2048×1536，主点缩放：
   `cx' = 720 * 2048/1440`，`cy' = 540 * 1536/1080`。焦距像素同样按宽度比缩放。畸变先当 0（XMP 全 0）；`survey` 再从报告或自标定接入 k1–k3。
4. 输出格网原点对齐厂商习惯：北向上 GeoTIFF，`AREA_OR_POINT=Area`。
5. 主波段默认 550 nm；某帧缺绿波则降级 RGB 亮度。
6. 多光谱 uint16 原样重采样，不拉伸、不匀色、不转 8 bit。

### 6.3 质量报告对齐 LiMapper

PDF 只放摘要，JSON 放全量。最少包含：

- 工程名、影像数、面积、平均航高、CRS、GCP 数  
- 分步耗时：解析 / 过滤 / 匹配 / 正射 / 镶嵌 / 写出  
- 2D 关键点总数、每影像均值、差影像列表  
- 连接点数、未采用帧  
- GPS 残差 RMSE（X/Y/Z）——**报告，不作为 10 cm 门槛**  
- 航向/旁向重叠率  
- **波段套合：每波段 25 个棋盘格点，相对绿波段的均值/RMSE（像素）** ← 这是 30 分钟档的硬指标  
- 输出文件清单与 GSD

## 7. 10 km × 100 m / 30 分钟预算

### 7.1 规模

110 m 航高、GSD 0.05 m 时单帧地面约 102 m × 77 m。100 m 宽 **一条航带够**。航向重叠 70% 时间距约 23 m → **约 430–500 曝光**。加 7 个光谱 ≈ 4000 个栅格文件，与当前 671 帧测试集同量级。

当前测试折线已有 8.7 km，是 10 km 目标的最佳开发集；先在这套数据上把墙钟打到 20 分钟以内，再扩到 10 km。

### 7.2 `fast` 时间表（16 核、64 GB、NVMe、无 GPU）

| 步骤 | 做法 | 预算 |
| --- | --- | --- |
| 解析 4000 文件 XMP/GPS | 只读标签，不解码像元 | 1 min |
| 过滤 | 倾角、白板、统计抽检 | 0.5 min |
| 主波段顺序匹配 | 500 对，1/2 分辨率 ORB | 6 min |
| 位姿 refinement | 小 BA 或逐帧仿射 | 1 min |
| 正射主波段 | OpenCV remap，16 线程 | 4 min |
| 其余 7 路拷贝几何 | 同一 map，流式 | 8 min |
| 羽化写出 COG | 分块，GSD **0.10 m** | 6 min |
| 报告 | 抽点 + PDF | 1.5 min |
| **合计** |  | **约 28 min** |

**0.05 m 全分辨率写出** 会使镶嵌+IO 再翻倍，30 分钟档默认 **0.10 m**（仍远细于现有融合文档的 0.3 m）。需要 5 cm 时：加 GPU，或接受 45–60 分钟。

禁止事项（否则必超时）：

- 8 个波段各自做空三  
- 整景载入内存拼数组  
- scipy `map_coordinates` 做正射  
- 把 8 通道重采样到厘米级 RGB 再配（旧融合文档已禁止）  
- `survey` 密集点云计入 30 分钟

### 7.3 内存

10 km × 100 m @ 0.10 m → 约 1e8 像元。uint16 × 7 波段 ≈ 1.4 GB；RGB uint8 ≈ 0.3 GB。必须 **分块 COG 写出**，正射按帧、按窗口，禁止分配整景 8 通道立方体。

## 8. 分阶段交付（按可验收切片）

### 阶段 0 — 目录与金标准（约 1 天）

- 写 `catalog.py`，在 `MAX_20251017` 上断言：671 GPS、CaptureUUID 成组、白板 2 帧、CRS 候选 32647。  
- 用厂商 `拼图结果/Orthomosaic_pix_surf_group0.tif` 做目视金标准，不要求像素级一致。

### 阶段 1 — POS 直投能上地图（约 3 天）

- 每帧 XMP → UTM 仿射（含 yaw）。  
- 主波段 + RGB 各出一张粗糙镶嵌。  
- 验收：QGIS 叠在厂商 DSM/正射上，平面偏差允许数米（GPS 级）。  
- 这一步就是方案 B，作为保底交付。

### 阶段 2 — 条带匹配 + 波段共用几何（约 1 周）— **30 分钟主路径**

- `match_strip` + `band_transfer`。  
- 验收：绿 vs 650/850 相对 RMSE < 2 像素；RGB vs 绿 < 3 像素（RGB 与多光谱不是同一传感器，略放宽）。  
- 在本机对 `MAX_20251017` 打墙钟，目标 < 20 min @ 0.10 m。

### 阶段 3 — 报告与目录契约（约 2 天）

- `quality.json` + `quality.pdf`，目录结构按 REQ-06-03。  
- 对照 `0611hsl_Report.pdf` 缺章补章。

### 阶段 4 — `survey`（可选，不挡 30 分钟）

- 2.5D 点云 / 拼接线 / 自标定畸变。  
- 有 GCP 后再打开 REQ-05-01 绝对精度。

| 辐射定标、白板反射率、指数 | 拼图完成后再走 L1/L3；本任务假定「预处理已完成」 |

不要把本任务塞回 `run_fusion.py`。那条流水线的输入是独立 POS CSV + 已是条带的 GeoTIFF，和 MAX 单帧目录不是同一种数据。

## 10. 风险与对方需确认的口径

1. **2 像素是相对套合还是绝对 GPS** — 建议相对；绝对必须 GCP 或 RTK。  
2. **30 分钟默认 GSD = 0.10 m** — 5 cm 为质量档。  
3. **密集点云 / 智能拼接线不进 30 分钟** — 写进协议，避免按 LiMapper 全功能验收。  
4. **10 km 若飞成多航带面状**（旁向也 100 m 以上、上千曝光），30 分钟只保证一条 10 km×100 m 走廊。  
5. **主点缩放** 是根据 LiMapper 1440×1080 与实图 2048×1536 的推断，阶段 0 要用厂商正射反投验证；若对方有 MAX-S810 标定 XML，优先用官方文件。

## 11. 立即可以开始的第一刀

有了帧表，后面匹配、正射、报告都沿同一份目录生长。
