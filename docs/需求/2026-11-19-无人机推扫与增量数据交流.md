# 无人机推扫数据与拼图服务交流稿

日期：2026-11-19  
对象：无人机数据侧  
材料：`docs/需求/无人机数据/` 下 5 个架次目录，外加现有拼图服务的框幅输入和增量收片  
用途：把「这批文件是什么」和「现有拼图服务吃什么」对齐，并列出必须当场确认的点。本文数字都来自这批文件本身，不是相机宣传页。

---

## 1. 先对齐的结论

现有拼图服务处理的是**框幅多光谱照片**：一次曝光一张图，文件名是 `MAX_<曝光号>_(Color|波长nm)_[DWR].jpg/tif`，位置姿态写在每张片子的 EXIF/XMP 里。算法是特征匹配、空三、密集匹配、DSM、正射镶嵌。

这批无人机数据是**彩谱 FigSpec FS-60C 机载推扫高光谱**。一次飞行写成一个 ENVI 立方体，不是一堆照片。空间上只有一条缝（960 个像元），飞行过程中按行往下扫；光谱是 600 个连续波段，约 390–1003 nm，大约 1 nm 一个。定位不在立方体里，在旁边的 `figspec.gps`，大约 1 秒一条，一条对应约 70 行。

厂家软件已经能把其中一个架次拼成带经纬度的成果立方体（`MergeResult0414`）。那是另一条几何链路：按行直接地理编码，再把航带铺到地图格网上。现有空三正射管线接不了这种文件，现有「增量拼图」也认不了这种文件名。

增量这两个字在两边不是同一件事：

- 拼图服务里的增量，是照片陆陆续续到齐后，**在同一条任务上整幅重跑**。空三和正射算法没有做成「只补新到的那几张」。
- 推扫如果要实时，数据是**一个正在变长的立方体**（大约 70 行/秒、80 MB/秒），不是一张张到齐的照片。

明天讨论建议先定三件事：
1.对方要的产品是「600 波段地理编码立方体」，还是「像现在这样的正射 GeoTIFF + DSM」；
2.实时指的是落地后按航带补文件，还是飞行过程中按行出图；
3.`pixel size`、姿态四列、白板文件的单位和含义。

## 3. 文件里各是什么

一个能用的原始架次是三件套，文件名固定，不带架次号：

### `figspec.hdr` + `figspec.spe`

标准 ENVI 头加裸数据。头是文本，数据无头偏移。

`samples = 960` 是狭缝方向（旁向）的像元数。`lines` 是飞行中扫出来的行数，时间顺序，不是地图上的南北行。`bands = 600`。

BIL 的排布是：每一行里，先放第 1 个波段的 960 个像元，再放第 2 个波段的 960 个，直到 600 个波段。一行大小：

```text
960 × 600 × 2 字节 = 1,152,000 字节 ≈ 1.10 MiB
```

70 行/秒时，原始流大约 **77 MiB/秒（约 80 MB/秒）**。按行读是连续的；按单个波段读整幅，则要在文件里跳着读。后面做几何时，自然的处理单位是「一行的全部波段」，不是「一个波段的整幅图」。

字节数和头一致，例如 0414：

```text
960 × 30962 × 600 × 2 = 35,668,224,000 字节
```

原始头里**没有**地图坐标、没有 `map info`。只靠 `.spe` 无法落到地上。

头里和辐射、几何有关、明天要逐项确认的字段：

| 字段 | 原样 | 我们现在的理解 | 要确认 |
| --- | --- | --- | --- |
| `pixel size = 5.86` | 没写单位 | 按微米理解才和 25 mm 镜头、80 m 航高对得上 | 单位；这是合并前的像元还是合并后的像元 |
| `space binning = 2` | | 960 已经是合并后的像元数 | 合并是在相机里做完的，还是软件后又做了一次 |
| `spectrum binning = 2` | | 600 波段已是光谱合并后的结果 | 原始光谱通道数、合并规则 |
| `focal length = 25` | 没写单位 | 按毫米，才得到厘米级地面分辨率 | 单位；是名义焦距还是标定焦距 |
| `flight height = 80` | | 相对地面的作业设定。GPS 绝对高度在 142 米附近 | 80 相对哪一个地面；有没有地形 |
| `exposure time = 8000` | 没写单位 | 若是微秒，就是 8 ms。行周期约 14.3 ms，8 ms 放得下 | 单位 |
| `deducting dark current = False` | | 原始立方体是 DN，没有扣暗电流 | 暗电流文件在不在、要不要我们扣 |
| `gain = 0` | | 增益档 0，不是反射率 | 0 的定义 |
| `default bands = {208,150,48}` | 1 起算的波段号 | 大约 601 / 542 / 438 nm，用来做假彩色 | 只是显示，还是处理主波段 |

假彩色波长按波长表线性估算：第 208、150、48 波段（从 1 数）落在大约 601、542、438 nm。成果立方体的 `default bands` 换成了 `{257,150,58}`，显示用的三个波段和原始不一样。

### `figspec.gps`

文本表，逗号分隔。能用的四份表头相同：

```text
Lines,UnixTime,Microseconds,Latitude,Longitude,Altitude,W,X,Y,Z,XVelocity,YVelocity,ZVelocity,UAVTimeMs,SysUnixTime,SysMicroseconds
```

0414 的第一行数据：

```text
119,1776144944,800000,35.1314914678087,113.765048172065,142.204833984375,0,398,-378,143,0,-2,-6,320163000,1776145507,6840854
```

各列从数据里能确定的事实：

| 列 | 事实 |
| --- | --- |
| `Lines` | 立方体行号，不是从 0 开始。0414 从 119 到 30923，立方体一共 30962 行。开头几十行和结尾几十行没有 GPS |
| `UnixTime` + `Microseconds` | GPS 时刻。相邻记录几乎都是正好 1 秒。微秒多数是 800000，偶发 807000、809000、810000 |
| `Latitude` `Longitude` | WGS84 度。1 秒位移约 2.60 米 |
| `Altitude` | 绝对高度，米。一次飞行内变化小于 1 米。不是头文件里的 80 |
| `W,X,Y,Z` | W 全是 0。X/Y/Z 是整数，整条航线（含往返）的中位数大约 400 / -381 / 125，往返时并不跟着航向转 180°。不像单位四元数（单位四元数的 W 不能恒为 0，这四数的模也不是 1）。更像某个坐标系里基本不变的云台角，外加转弯时的野值（X 会到 -552，Y 会到 560） |
| `XVelocity,YVelocity,ZVelocity` | 小整数。水平两列大多在 ±10 以内，合成后对不上 2.6 m/s 的地速。Z 在长航线里会出现 ±170 一级的尖峰。单位不能当成 m/s |
| `UAVTimeMs` | 名字像毫秒。相邻 1 秒记录的差值中位数约 1.01×10^6，和微秒更接近。0414 从 320163000 到 765755000，差值约 446 秒，和飞行 441 秒接近 |
| `SysUnixTime` | 比 GPS 的 `UnixTime` 大约晚 **560–576 秒**（9 分多钟）。不像写盘延迟，更像另一套钟。目录名上的当地时间和 GPS 时间一致，和这列不一致 |

行号差的中位数是 70，时间差是 1 秒，所以扫描率是 **70 行/秒**。GPS 没有给到每一行。要把立方体铺到地面，必须在两条 GPS 之间为另外约 69 行插值位置；姿态如果参与几何，也得同样插值。转弯段的插值不能当成直线。

只有 2026-04-14 这一架带了厂家拼图结果，时间戳在成果 TIFF 上是 `2026:04:17 18:42:36`，软件标记 `v1.0.0`。原始飞完到出这个文件，隔了大约三天，**不能**把它看成实时产品。

| 文件 | 内容 |
| --- | --- |
| `MergeResult0414.hdr` + `.spe` | 2291 × 6578 × 600，uint16，BIL。体积 16.8 GiB，字节数和头一致。比原始短很多：原始 30962 行里的转弯被拿掉，五条航带铺到同一张格网上 |
| 地理信息 | 头里有 `geo points`（四个角：sample, line, 纬度, 经度）和 `cp gps matrix`（3×3，把像素变到经度、纬度）。原始头里没有这两项 |
| `MergeResult0414-RVI.tif` | 6578 × 2291、3 波段 uint16、EPSG:4326。地理范围北纬 35.13120°–35.13345°，东经 113.76343°–113.76463°。仿射和 `cp gps matrix` 一致。像元地面尺寸约 **3.7 cm × 3.8 cm**。文件名是 RVI，内容是三波段整数，中位数约 110，大约 18% 为 0，不是 0–1 的浮点比值 |
| `MergeResult0414.png` | 22 MiB 预览图 |
| `MergeResult0414.figspecwhite` | 8654 字节二进制。里面能读出的明文字有序列号 `FSW247022`、`bil`、`WhiteCorrection`、`Point`。不是一张可读的白板光谱表。只跟在成果旁边，原始架次没有 |

成果格网和飞行对得上：长边约 241 米（6578 × 3.67 cm），对应南北航带；短边约 86 米（2291 × 3.76 cm），对应五条航线的横向覆盖。飞机轨迹横向只有约 54 米，多出来的宽度是半个扫描幅宽，这和下面的地面分辨率是同一件事。

用这个矩阵时注意轴：GeoTIFF 的宽是 6578，高等于 ENVI 的 `samples` 2291。`cp gps matrix` 跟 GeoTIFF 的列、行走，也就是矩阵的列对应 ENVI 的 `lines`，行对应 ENVI 的 `samples`。直接拿「sample, line」去乘矩阵，方向是反的。四个 `geo points` 可以用来核对。

## 4. 和现有拼图服务差在哪里

现有服务的输入和算法，以已接入的 MAX 框幅测区为准（见 `docs/自研摄影测量架构设计.md` 和增量收片代码）。

| | 现有拼图服务 | 这批推扫数据 |
| --- | --- | --- |
| 成像 | 一次曝光一幅二维照片。RGB 与多光谱都是框幅，设计文档里的测区是 2048×1536 | 一次曝光一行。960 个空间像元 × 600 个光谱像元，飞行把行堆成立方体 |
| 一次任务的文件 | 几百到几千张 `MAX_曝光号_波段_角色.jpg/tif`。角色里有白板帧 | 一个架次三个文件：`.hdr` `.spe` `.gps`。文件名不带曝光号 |
| 光谱 | 离散通道。需求材料里的 MAX 样机是 RGB 加 7 个通道，大约 450–850 nm | 连续光谱 600 波段，390–1003 nm，间隔约 1 nm |
| 定位 | 每张片子自己的 EXIF/XMP：经纬高、航向、俯仰、横滚 | 旁路 CSV，1 秒一条，用 `Lines` 对上立方体行号。没有逐行姿态的明文定义 |
| 重叠从哪来 | 相邻照片之间的航向重叠、旁向重叠。空三靠同名点 | 行与行是时间相邻，不是照片重叠。重叠发生在**航带与航带之间** |
| 几何主路径 | GNSS/INS 给外方位初值，再特征匹配、光束法平差、密集匹配、DSM，按 DSM 做正射 | 厂家成果走的是直接地理编码：每行一个位置，重采样到经纬度格网。这批成果头里没有 DEM/DSM 字段 |
| 一个架次的产品 | 每个波段一张正射 GeoTIFF，加 DSM、质量报告 | 一个 600 波段地理编码立方体，外加一张 3 波段 GeoTIFF 和一张 PNG |
| 辐射 | 多光谱明确不做色彩拉伸，保留原级数 | 头文件写明没扣暗电流、增益为 0。白板文件只有成果那一份，而且是私有二进制。原始值应仍是 DN |
| 增量收片认不认 | 只认上面的 MAX 文件名。文件大小连续两次不变才算传完，然后**整幅重跑** | 文件名、结构、体量都不符合。一个 33 GiB 的文件在飞行中会持续变大，按「大小不变」会一直被视为没传完 |

现有增量的实现边界，避免会上说成「已经能实时拼」：

- 收件目录在正式目录旁边，扫的是照片文件。
- 新片子并进同一个测区、同一条任务。
- 重跑时新开输出目录，清掉续跑标记，`run_mode = full`。日志原文是「正式目录有新航片，在同一条任务上重新拼」。
- 它解决的是「片子分批到」，不是「立方体按行增长」，也不是「只重算新到的那一条航带」。

因此有两道不同的缺口：

1. **格式和几何模型。** 即便全部落地、一次性给齐，现有 catalog 也不会收 `.spe`，空三的「一张照片一个外方位」也不等于「一行一个外方位」。
2. **到数方式。** 即便以后做了推扫地理编码，现有收片状态机仍然按「照片大小稳定」工作，接不住 70 行/秒的追加写。

## 5. 从这批文件算出的飞行几何

下面用的是头文件数值和 0414 的 GPS。像元尺寸、焦距、航高的单位头文件都没写，下表按微米、毫米、米。这个组合能和成果像元对上；若单位不是这样，这张表作废，所以它同时是问题清单。

旁向地面分辨率：

```text
GSD = 航高 × 像元尺寸 / 焦距
```

| 理解 | 参与计算的像元 | 旁向 GSD | 960 像元幅宽 |
| --- | --- | --- | --- |
| 5.86 已经是合并后的像元 | 5.86 μm | 1.88 cm | 18.0 m |
| 5.86 是合并前，空间合并 ×2 后像元加倍 | 11.72 μm | 3.75 cm | 36.0 m |

沿航向采样和相机幅宽无关：

```text
2.60 m/s ÷ 70 行/秒 = 3.71 cm/行
```

厂家成果的像元是 3.7 cm × 3.8 cm，和沿航向采样一致。

和覆盖宽度对照：

- 飞机轨迹横向跨度约 54 米，成果图横向约 86 米，两边多出来约 16 米，接近「半个 36 米幅宽」。
- 航线间距 12–15 米。若幅宽 36 米，旁向重叠大约六成；若幅宽只有 18 米，重叠大约两成，而且解释不了成果为什么有 86 米宽。

更说得通的是第二条：`pixel size` 是合并前的像元，960 是合并之后的空间像元，旁向大约 3.7 cm、幅宽大约 36 米。明天用一句话确认即可。

曝光若确为 8 ms，地速 2.60 m/s 时，一行里的位移约 2.1 cm，小于 3.7 cm 的成果像元。原始 DN 没有扣暗电流，讨论反射率或植被指数之前要先问校正做在哪一步。成果立方体的显示阈值（`default thresholds = {892,894,218}`）比原始（`{600,30,90}`）高，只能说明显示拉伸变了，不能说明数值已经变成反射率。

## 6. 0410 这套现在不能用

`FigSpec_260410_142436` 的 `.spe` 大小是 37,440,000,000 字节，刚好是 `32500 × 960 × 600 × 2`。数据体看起来还在，旁边两份文件不是有效旁车：

- `figspec.hdr` 不是 ENVI 文本。文件头是 Mac 的 AppleDouble 资源叉（里面有 `Mac OS X` 和 `This resource fork intentionally left blank`）。波长、焦距、行数都读不到。多半是从 macOS 拷贝时把 `._figspec.hdr` 当成了头文件。
- `figspec.gps` 没有 `Lines,UnixTime,...` 表头。文件开头是一段 scikit-learn 训练日志（`Best parameters: {'max_depth': 10, ...}`，以及 R2、MSE）。表头位置被别的程序输出盖住了。

这一架先不要拿来对算法。需要对方按 0414 的样子重传头文件和 gps。重传前不要从文件名猜测它和另外几架是同一块地。

## 7. 明天建议问的问题

按这个顺序问。前两组决定做不做、做成什么样；后面几组决定几何和辐射能不能算。

### 产品到底是哪一种

1. 要的成果是厂家这种 **600 波段 ENVI 立方体**（可再导出若干指数），还是现有服务这种 **分波段正射 GeoTIFF + DSM + 质量报告**？两套产品的算法不是同一个。
2. 推扫这套还要不要 DSM？厂家这份成果只有经纬度仿射，没有高程。平坦耕地可以先不做 DSM；有坡度、房屋、树高时，只靠 80 米航高的平面投影会有旁向位移。
3. 600 个波段是都要保留，还是最终只用少数波段和指数？这决定内存和成果体积（一个架次原始 33 GiB，拼完仍有 17 GiB）。
4. 三天三次飞同一块地，是重复观测（要比辐射变化），还是只是样例飞了三次？短航线 `135339` 是不是另一块地的单条测试。

### 「实时增量」指哪一种时序

5. 实时是飞机还在飞就出图，还是落地后按航带把文件交过来？
6. 若是飞行中：立方体是一个文件一直追加，还是每条航带（或每 N 秒）切一个新文件？GPS 是跟着行一起到，还是另一条更慢的流？
7. 能接受的延迟是一行、一条航带，还是整架次？70 行/秒、约 80 MB/秒，是按这个量级准备链路，还是机上先降采样、抽波段再传？
8. 增量的粒度是「新航带铺上去、旧航带不动」，还是「来一批就把整块地重拼」？现有服务只能做后者，而且对象是照片。

### 几何参数

9. `pixel size = 5.86` 的单位，以及是不是空间合并之前的像元。确认后幅宽才是 18 米或 36 米里的一个。
10. `focal length = 25`、`exposure time = 8000`、`flight height = 80` 的单位。80 米相对起飞点、相对地面，还是相对椭球？
11. 狭缝方向：960 这一维是垂直于航向还是沿航向？镜头畸变、主点、狭缝在焦平面上的位置有没有标定文件？
12. `W,X,Y,Z` 是什么（欧拉角、四元数、云台角），单位和坐标系，W 恒为 0 是否表示无效或未使用。往返航向差 180°，而这三列的中位数几乎不变，需要他们解释。
13. 速度三列的坐标系和单位。为何对不上由经纬度算出的 2.6 m/s。
14. `UAVTimeMs` 到底是毫秒还是微秒。`SysUnixTime` 为什么比 GPS 时间晚大约 9 分钟，拼接时该信哪一个钟。
15. GPS 的 `Altitude` 是椭球高还是海拔？平面精度、是否 RTK。1 秒一条时，中间 69 行是允许我们线性插值，还是机上已有更高频率的惯导可以提供。
16. 转弯段算不算有效成像。原始立方体把转弯包在里面；厂家成果显然把转弯裁掉了。裁切规则是什么（航向角、速度、云台状态）？

### 辐射

17. 原始 `.spe` 是否确定为未校正 DN（与 `deducting dark current = False` 一致）？
18. 暗电流、白板、辐射定标系数的文件格式。`figspecwhite` 能否给读法，还是只作为厂家软件的私有输入。
19. `MergeResult0414.spe` 里的数已经是反射率，还是仍然是 DN，只是几何上拼过？`RVI.tif` 三个波段分别是什么，有没有比例尺（例如 ×10000）。
20. 重复飞行之间，曝光和增益是否允许变。这三架头文件里这几项相同，需要确认实际没有改。

## 8. 会上可以怎么谈「接进来」

只作为交流口径，不是工期承诺。三条路互斥程度很高，最好让对方选主产品，而不是三条一起做。

**甲。接收厂家已经拼好的立方体。**  
输入就是 `MergeResult` 这种带 `geo points` / `cp gps matrix` 的 ENVI，加上说明数值是 DN 还是反射率。我们这边做的是入库、按波段或指数出 GeoTIFF、套到地图上。不重做几何，也不产生 DSM。这和现有正射管线几乎无关，工作量在读取 BIL 和仿射。实时只能做到「厂家拼完一航带，我们收一航带」，实时性取决于厂家软件，不取决于我们现在的收片目录。

**乙。从原始三件套做直接地理编码。**  
用 gps 把每一行投到地面，航带之间按重叠镶嵌，输出和厂家成果同类的地理编码立方体。前置条件是第 7 节里像元、焦距、姿态、时间戳都有明确单位。平坦地形可以先用航高平面；要抗地形就得有 DEM，或接受旁向误差。这条路**不经过**现有的特征匹配和 DSM 正射。现有增量收片也要另做：至少按「航带文件写完」触发，而不是按 MAX 照片名。

**丙。把推扫行切成假的框幅照片，送进现有空三。**  
几何模型对不上。推扫是每行一个投影中心，切成照片后，一张「照片」里的每一行本来就有不同的外方位，现有的「一片一个外方位」会把这个差吃掉。重叠方式也不一样。不建议把这条当作主路径。只有在对方明确要建筑物级别的 DSM、并且能提供可当框幅用的第二台相机时，才再谈现有管线。

和「实时」的对应关系：甲、乙若要做到飞行中更新，都要先有稳定的行流或航带文件约定。现有服务的增量是照片到齐后整幅重跑，对 33 GiB 立方体既认不出文件，也不能在文件还在增长时开算。

## 9. 知识点扫盲

下面只保留明天会碰到的词。每条先说它是什么，再说它在这次讨论里落在哪。

### 框幅和推扫

框幅相机像普通照相机，一次曝光得到一幅完整的二维图像。相邻两张要有重叠，才能用同名点把它们拼起来。现有拼图服务的 MAX 照片是框幅。

推扫（也叫线阵、扫帚式）像扫描仪。焦平面上只有一条缝，飞机往前飞，缝在地面上扫出一条带子。每一行有自己的位置和姿态。高光谱里很常见，因为狭缝后面要用光栅把一条线的光散成很多波长。这批 FS-60C 就是这种：`lens adjust mode = line`，`samples` 是缝上的 960 个点，`lines` 是飞出来的行。

后果：框幅拼图依赖照片之间的重叠和同名点；推扫拼图依赖每一行的位置姿态，以及航带和航带之间的旁向重叠。把推扫立方体当成「一张很长的照片」去做特征匹配，转弯和行方向的投影差都还在里面。

### 航带、旁向重叠、航向重叠

航带是飞机沿一个方向飞的一段。这批长架次是南北往返，0414 有 5 条，间距大约 12–15 米。

框幅相机同时有两种重叠：沿飞行方向，相邻照片重叠（航向重叠）；相邻航线之间也重叠（旁向重叠）。推扫在沿飞行方向没有「相邻照片」，行是连续扫的。它真正用来拼接的重叠是旁向：相邻航带的地面覆盖要压住一条。幅宽若是约 36 米、间距约 14 米，旁向重叠大约六成。短航线 `135339` 只有一条，没有旁向重叠，拼不出一块面。

### 高光谱和多光谱

多光谱是有限几个较宽的通道，例如红、绿、蓝、红边、近红外，各拍各的。现有需求和 MAX 样机是这种，大约 7 个光谱通道加 RGB。

高光谱是把一段波长切成几百个窄带，每个像元一条光谱曲线。这批是 600 带、约 1 nm、390–1003 nm，覆盖可见光到近红外。文件大，是因为每个地面点存了 600 个 uint16，而不是 3 个或 8 个。

处理含义：多光谱可以一个通道一张正射。高光谱更自然的成果是一个立方体，几何上所有波长共用同一行的位置。不要对 600 个波段各自做一次色彩均衡，否则光谱曲线就毁了。现有服务对多光谱「禁用色彩校正」这条原则，在高光谱上更要守住。

### 立方体和 BIL

立方体的三个轴是旁向像元、飞行行、波长。ENVI 用头文件描述裸数据怎么排。

三种常见排布：

- BSQ：一个波段一整幅，再下一个波段。适合单独拿一个波长出来。
- BIL：一行里 600 个波段排在一起。这批就是 BIL。适合「一行到了就把所有波长一起处理」。
- BIP：一个像元的 600 个波长排在一起。适合逐点取光谱。

这批一行 1.10 MiB，70 行/秒约 80 MB/秒。实时讨论时用这个数，而不是用「一张照片几兆」。

`data type = 12` 在 ENVI 里是 16 位无符号整数。`byte order = 0` 是小端。`header offset = 0` 表示 `.spe` 从第一个字节就是像元，没有文件头。

### DN、暗电流、白板、反射率

DN 是探测器读出的数字，跟光强有关，也跟曝光、增益、温度、暗电流有关。不同架次的 DN 不能直接当生物量去比。

暗电流是没有光时也有的底。头文件写 `deducting dark current = False`，表示这份立方体没减这个底。

白板（白参考）是一块反射率已知、尽量接近全反射的板。用它把 DN 换成反射率，常见形式是 `(DN − 暗) / (白板 − 暗)`。成果旁边的 `.figspecwhite` 从名字和内部明文看是白板校正记录，但是私有二进制，原始架次目录里没有。在读懂它、并确认成果立方体是否已经除过白板之前，不要把 `.spe` 里的数叫作反射率。

增益 0、曝光 8000 在三次长航线的头里相同。若现场其实改过曝光而头没改，重复飞行之间的 DN 差异会混进地物变化。

### 直接地理编码和空三

直接地理编码：相信 GPS/惯导给出的位置和姿态，用焦距和像元大小，把每个像元投到地面，再重采样到规则格网。厂家这份 `MergeResult` 就是结果，证据是头里的角点和 3×3 矩阵，以及和它一致的 GeoTIFF。

空三（光束法平差）：用照片之间的同名点，把每张照片的位置姿态和地面点一起估一遍。GPS 只是初值和约束。现有服务走的是这条，因为框幅照片有重叠，而且这批 MAX 数据的地形起伏大，必须有 DSM 才能正射。

推扫也可以做带控制点或同名点的平差，但模型是「一行（或一段）一个外方位」，不是现有代码里的「一帧一个外方位」。明天不要把「我们已经有空三」说成「推扫几何已经覆盖」。

### GSD、航高和这批里的两个「高度」

GSD 是一个像元在地面上的边长。`GSD = 航高 × 像元尺寸 / 焦距`。航高是相机到地面的距离，不是 GPS 里的绝对高度。

这批里两个数不要混：

- 头文件 `flight height = 80`：作业设定，更像离地高度。
- GPS `Altitude ≈ 142` 米：绝对高度，飞行中几乎不变。

地面分辨率还分两个方向。旁向由镜头和像元决定，按第 5 节大约是 1.9 cm 或 3.7 cm。沿航向由地速和扫描率决定，这里是 3.71 cm。两边不相等时，立方体里的「一个像素」不是地面上的正方形。厂家成果把两边都重采样到了约 3.7 cm。

### 姿态：欧拉角和四元数

欧拉角是航向、俯仰、横滚三个角，会随飞机掉头而变。四元数是四个数 `(w, x, y, z)`，描述同一个旋转，单位四元数满足 `w²+x²+y²+z² = 1`，一般 `w` 接近 ±1（小角度时）。

这批 `W,X,Y,Z` 对不上这两种的直接读法：`W` 恒为 0，其余是几百的整数，模不是 1；飞机南北对飞时中位数几乎不变。讨论几何之前先让对方给定义，不要在会上假设它是四元数。速度三列同样先问单位，不要参与计算。

### 时间戳

至少有三套时间：

- GPS 的 `UnixTime`，和目录名上的当地时间（UTC+8）一致，飞行时刻以它为准最合理。
- `UAVTimeMs`，量级像微秒计数器，用来和行号对齐可能有用，但是名字和数量级矛盾。
- `SysUnixTime`，比 GPS 大约晚 9 分钟，更像机载电脑的钟。

实时增量如果用「系统时间」做切割或延迟统计，会和飞控时间差这 9 分钟。要对齐行号，优先用 `Lines` 和 GPS 时间，而不是系统时间。

### 正射、DSM，以及这批成果不是正射

正射影像是消掉倾斜和地形起伏之后，每个像素都垂直投影到地面的图。现有服务用 DSM（包含房屋、树冠的表面高程）做这件事。没有可靠高程时，高的地物会朝远离像底点的方向偏移。

这批厂家成果是一个地理编码立方体：格网是经纬度，像元大约 3.7 cm，但头里没有高程面。在 80 米航高、地面平坦时，它看起来像一张拼好的图；有地形或高杆作物时，它不等于现有服务说的正射。RVI 那张 TIFF 只说明「有人把同一格网写成了三波段 GeoTIFF」，文件名不能代替波段定义。

EPSG:4326 是经纬度，单位是度。成果里一个像元在经度、纬度上的步长不同，但换算到地面大约都是 3.7 cm。真要量面积或和现有 UTM 成果对齐，还要投影，不能把度的差值当成米。

### 植被指数（RVI）

RVI 通常是近红外反射率除以红光反射率，用来看植被长势。它应该建在反射率上，至少也要建在同一套定标后的值上。两个波段若只是未校正 DN，比值里会留下曝光和光谱响应的差别。

文件 `MergeResult0414-RVI.tif` 是 3 波段 uint16，不是单波段浮点比值。会上把它称为「一份三波段地理产品」，波段含义和缩放比例向对方要，不要按教科书公式去读像素值。

### 现有「增量拼图」实际做什么

数据增量：文件分批到达。  
算法增量：新数据来了，只更新受影响的那一块，旧结果不动。

现有功能是数据增量、算法全量。照片名必须符合 `MAX_<数字>_(Color|波长nm)_[DWR].jpg/tif`。大小连续两次扫描不变，才从收件目录拷进正式目录。一个测区只绑一条任务；再来新片子，就在这条任务上从头跑，并换一个新的输出目录，避免沿用上一次的空三缓存。

所以对无人机同事可以这样说：服务能「边传边等、到齐就重新拼照片」，不能「边飞边把推扫行补进同一张高光谱图」。若他们要的是后者，收片、几何和成果格式都要单独约定，不能在现有增量开关上改一个参数完成。
